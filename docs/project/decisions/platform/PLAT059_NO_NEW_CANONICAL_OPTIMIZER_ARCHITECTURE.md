# PLAT059 — No additional canonical-optimizer architecture required

## Owner-approved clarification — 2026-10-15: canonical Core selection

**Approval provenance:** In the active PLAT059/I101 correction conversation, the project owner explicitly approved replacing the overbroad "ordinary messages may be overridden" objection with the **Canonical Core Dispatch Invariant**, and approved propagating it to the normative specification, I101 and agent instructions. This is a bounded clarification of canonical Core behavior, **not** authorization for another optimizer architecture, not proof that every send is pure, and not a change to custom-object dispatch.

**Canonical Core Dispatch Invariant (binding I101 admission criterion):** For an exact canonical Boolean or Number value, standard method selection follows its specified delegation chain and the published, frozen standard Core owners. For the canonical operations installed there (e.g. `Object.ifTrue`, `Object.if`, `Integer.+`, and `Number.<`, `Number.<=`, `Number.>`, `Number.>=`, `Number.==`), a guest-defined same-named slot on a **different ordinary object**, or lexical shadowing of the visible prototype name, does **not** modify the actual method selected by that canonical value. The Core publication contract, not a per-send speculative runtime guard, establishes this invariant. Distinguish a canonical *value* from an ordinary object that happens to delegate to a numeric value or standard prototype.

**Required lowering consequence:** When a NORMAL lowering proof establishes the exact canonical receiver, standard selector, sufficient exact operand values and no discarded guest-visible effects or control transitions, emit the canonical result or inlined body **directly, with no message send, Assumption guard or fallback** whose sole rationale is a hypothetical override of the frozen Core implementation. Examples: `1 + 2 -> 3`, `1 < 2 -> true`, `1 == 1 -> true`; `true.ifTrue() { 1 }` may produce the literal-one execution body under the existing PLAT058 oracle contract. `true.if() { ... }` must preserve the selected callback's effects and returns canonical `true`, not the callback result (D200). Preserve the precise numeric and Boolean semantics, including overflow, mixed families, invalid operations and evaluated arguments.

**Limits:** An unknown or user-defined receiver, a mutable/absent/recreated lexical binding, a call whose effective selection is genuinely unknown, or observable evaluation/invocation effects still requires ordinary D013/D179 semantics and guarded/generic lowering as appropriate. `==` remains an overridable method on arbitrary receivers and is not redefined as `===`; the static canonical Number case is different. Preserve DEBUG, full source and control obligations and deterministic Bytecode DSL reparse. Do not add a guard merely because a selector is spelled as an ordinary message; show a **legal, applicable** mutation or alternative selection affecting this receiver if a canonical fold is to be blocked. The handwritten Builder oracle and independent semantic regressions remain mandatory.

**Scope and publication:** PLAT059 remains `NO_NEW_ARCHITECTURE_REQUIRED` and closed; PLAT058-D remains authoritative. Existing historical GITHUB010 evidence and the 2026-10-14 approval are retained. This clarification supersedes only the overgeneralized caution about canonical literal sends below; I101-A/B remain published, and I101-C must apply the clarified criterion. The normative `spec/semantics/OBJECT_MODEL.md` clarification and product `AGENTS.md` guidance are approved but require human publication in `guillermomolina/protos`; this project-docs record is not a substitute for that normative commit.

## Approved disposition and scope

1. **Keep PLAT058-D authoritative.** One shared proof-driven Canonical → Truffle Bytecode DSL lowerer; immutable Context-owned NORMAL/DEBUG physical-compilation profiles; deterministic/idempotent reparse; no runtime mode branch in admitted profile-fixed paths; minimum justified physical emission **before** Graal; every claimed elimination needs an independent handwritten Bytecode DSL Builder oracle including whole executable signature and root-group topology.
2. **Implement only justified current needs under I101-B/C.** Extend existing local immutable proof/emission decisions, binding/escape/suspension analyses, Boolean and Closure optimizations and admitted small pure arithmetic. Do not duplicate I101's existing implementation owner, create micro-slices or reimplement PERF043's scoped Integer optimizations.
3. **Defer a dedicated global/pre-bytecode canonical value/effect optimizer.** A bounded immutable per-site fact analysis (without rewriting the original Canonical AST) is an optional future candidate *only if* repeated cross-statement fact needs or duplicated proof work cannot be handled economically by the approved design. Such a materially new architecture would require a separate explicit owner decision, GITHUB010/GITHUB021 assessment and durable ratification.
4. **Reject a wholesale rewritten optimized Canonical AST as current scope.** Its additional node identity, source, Closure-root, binding-analysis, DEBUG and reparse integration risks are disproportionate to current proved needs.
5. **No observable semantic change; canonical Core dispatch is fixed.** An exact canonical receiver whose standard method selection is fixed by the published frozen Core may be folded without runtime dispatch when its exact operands and effects are also proved. Shadowing/overriding selectors on distinct custom objects does not invalidate this. D179 `PRESENT`/`ABSENT`, capture and shadowing, side effects, ReturnHome, suspension/cancellation, Context and DEBUG remain binding outside proven cases. Keep genuine dynamic dispatch and fallback where required; do not introduce fallback for an impossible canonical override. See the owner-approved 2026-10-15 clarification above.
