# PLAT081 — Buffered byte I/O implementation ownership

- Decision: [PLAT081 / #1213](https://github.com/guillermomolina/protos/issues/1213), phase C of [AUD025 / #1209](https://github.com/guillermomolina/protos/issues/1209).

## Approved boundary

Retain the existing private runtime implementation of standard buffered byte I/O where buffer state participates directly in operation admission, commitment, cancellation, ordering, late-result reconciliation and lifecycle custody. Keep BufferedReader and BufferedWriter as explicitly imported Standard Library facilities under D167.

Higher-level protocol policies, framing, transformations and ordinary byte-processing algorithms should remain implemented in Protos whenever existing language mechanisms express their semantics.

Do not replace operation-owned C-prime execution with Task-backed continuations, introduce a parallel operation framework, expose new public primitives, or weaken existing I/O guarantees to facilitate source migration. No production Java migration is required solely to satisfy the Protos-first audit. Future source migration remains admissible if equivalent implementation using existing mechanisms can preserve all applicable contracts. Potential correctness defects are independent BUG investigations, not migration requirements.

No Java deletion quota, performance target or benchmark campaign is required. No follow-on I or D is warranted for this disposition.

## Invariant/delta consistency (GITHUB021)

The selected candidate preserves every applicable owner constraint recorded in #1213 and #1209: D167 library placement and exact frozen factory identities; ordinary public protocol semantics; long/double/boolean guest primitive constraint; specialized hot paths; isolation, mutable Bytes snapshots and fresh result identities; suspension; bounded admission and retention; ordered reads/writes/flush; resumable source EOF; unknown-effect failures without replay; close and owned release precedence; Actor termination and native completion safety. It retains PLAT028/029/030/031 ownership and C-prime scheduling and D112/D121 cleanup authority, and does not reopen D117 or D242. No new public contract, new Java infrastructure, speculative implementation issue, or normative delta is selected. Existing implementation defects are not legitimized by retaining the architecture. Any future production Java change still requires a verified exact method, annotation and behavior equivalent in GraalPy or another Truffle language.

## Comparative evidence and alternatives

GraalPy revision [21b9ad46ab3de0ee63960926e51b054e209fd3e3](https://github.com/oracle/graalpython/tree/21b9ad46ab3de0ee63960926e51b054e209fd3e3), package `builtins/modules/io`: `BufferedReaderMixinBuiltins.ReadNode.readFast` (guarded @Specialization), `FillBufferNode.bufferedreaderFillBuffer` (@Specialization, @GenerateInline class), `RawReadNode.bufferedreaderRawRead` (@Specialization), `BufferedWriterNodes.RawWriteNode.bufferedwriterRawWriteFileIO` / `bufferedwriterRawWrite` (guarded @Specialization), `FlushUnlockedNode.bufferedwriterFlushUnlocked` (@Specialization), `BufferedWriterMixinBuiltins.WriteNode.write` (@Specialization), `BufferedIOMixinBuiltins.CloseNode.doit` (@Specialization), and `BufferedIONodes.EnterBufferedNode` / `EnterBufferedBusyNode`. They establish specialized buffer storage, cursor and copy precedents, lower protocol invocation, synchronization and mandatory close. Python's raw write exposes progress; Protos ByteWritable does not. No equivalent new asynchronous producer/Actor infrastructure was demonstrated; do not invent it or copy GIL locking.

[TruffleRuby IO::InternalBuffer](https://github.com/truffleruby/truffleruby/blob/5d9b60ffb2229012c8dfb10cc70695e9ab3230d3/src/main/ruby/truffleruby/core/io.rb#L108-L252) demonstrates source-owned fill/shift/peek policy over ByteArray and private native primitives. It is the strongest argument for a future hybrid, but not proof of equivalent Protos cancellation or termination custody. [SimpleLanguage SLReadlnBuiltin](https://github.com/oracle/graal/blob/6539700e7a590d726992b21c3797e7ab9f6f992b/truffle/src/com.oracle.truffle.sl/src/com/oracle/truffle/sl/builtins/SLReadlnBuiltin.java) and [Apple Pkl ResourceReaders](https://github.com/apple/pkl/blob/c254bfbabeaed4d013009a7a3609a7f09d3eafb8/pkl-core/src/main/java/org/pkl/core/resource/ResourceReaders.java) are materially less comparable (host line reads and resource materialization). GraalJS/Node streams, Espresso/JDK, Sulong/native libraries, CPython, Go bufio, Rust/Tokio and asyncio were discussed at model level, not verified as exact production Java precedents.

A: retain existing boundary (selected); B: all-source migration (not equivalent using public Future/Task composition); C: hybrid source policy inside operation-owned C-prime (conceptually credible but no safe existing late-result mutation seam demonstrated); D: isolate pure helpers in source (possible arithmetic, but no demonstrated simplification of coordination and may add crossings); E: delegate to JDK streams (incompatible synchronous contracts). Existing A is smallest sufficient architecture, avoids imposing new costs on non-users, and defers only internal representation choices; future migration can be local and need not change public semantics. B is disqualified by correctness, C and D remain reversible options, and E would duplicate lifecycle adaptation. No global locks, new scheduler, hidden Task, new public primitive, speculative generic buffer facility or new Java implementation are justified.

Counterexamples: late lower read after cancelled outer read must preserve earliest bytes; failed write can contribute an unknown prefix and must not be replayed; a close racing unresolved first effect cannot claim zero effect; mandatory release after Actor termination cutover requires authorized cleanup; EOF of a growing file must not become permanently sticky; nested flush must propagate the ordered frontier. The existing common mechanisms protect these boundaries. Future backends, independent Contexts, larger workloads and Native Image need the same semantics, without pre-building unused infrastructure. A future proven source-owned storage seam could justify reopening only that implementation boundary.

## Independent static findings — reproduction pending

1. **Aggregated output admission.** `ProtosBufferedByteIo.write` lines 134–169 checks `snapshot.length > MAX_OUTPUT - output.length`. `Req.bytes` and the queue retain pending snapshots; `beginOperation` does not reserve byte capacity; `doWrite` lines 731–750 appends without rechecking aggregate capacity. With a held lower flush, many individually admissible writes can accumulate queued payloads despite the intended bound. Reproduce deterministically with a controlled pending lower Future, then test release on completion/cancellation/close and zero-effect capacity rejection under BYTE_IO §6.1. The numeric 1 MiB is private, not a new portable guarantee.
2. **Queued output after poison.** `failUnknownFirstEffect` and `poisonWith` lines 1114–1150 record `outputError` and retire the active request. Admission checks poison, but `pump`, `doWrite`, `doFlush` and `doFlushCPrime` do not visibly recheck it for already-admitted requests. A queued second flush may attempt to replay a prefix after the first lower write failed with unknown progress; queued writes may also commit after poison. Reproduce with two ordered flushes and controlled failure; distinguish failure from zero-effect cancellation and ensure owning close remains mandatory with primary Error identity.

These are concrete static hypotheses, not executed failures. Search for existing matching issues found no dedicated match. No new BUG identifier is allocated by this record; coordinate independent investigations when authorized. They do not require a new buffering architecture.
