## 1. Decision and why it exists

Protos needs secure bytes for independently implemented applications: per-password salts, session secrets, signing-key material and unpredictable tokens. An ordinary deterministic PRNG (even if implemented purely in Protos) is not a cryptographically secure host entropy source. The existing `std:crypto/sha256` module computes a digest; it does not mint random bytes.

**Selected C:** the host or embedding environment may explicitly provision one narrow secure-entropy resource to the **initial RootActor module context**. The bootstrap-local slot is `entropy`. Its possession is the authority to request cryptographically secure bytes. The slot is absent when not authorized, not bound to `null`. Access to imports, a Process object, filesystem/network/resolver permission or host source/package loading does not create entropy authority.

The user-facing standalone opt-in spelling presented and approved with C is **`--allow-entropy`**, for eligible application execution; the exact CLI mode matrix and option-parser mechanics must preserve the existing independent CLI grant and Tool boundaries. Embedding requires its own explicit host choice. No importable global generator, implicit `Math.random()`, public grant-minting constructor, uniform permission bundle or mandatory registry is created.

## 2. Minimal public behavior selected

The conceptual resource is an ordinary capability value with a narrowly defined lifecycle. The proposal reviewed for selection uses:

```protos
# Only when explicitly granted in the initial RootActor:
saltFuture: entropy.bytes(16)
secretFuture: entropy.bytes(32)
# An authorized Task may subsequently observe .value().
# No implicit suspension is introduced in Actor bootstrap.
```

- `entropy.bytes(count)` returns **`Future<Bytes>`** under the ordinary Protos Future and I/O-operation rules. On success it produces exactly `count` random octets, in a new, independent, mutable standard `Bytes` value (including a fresh empty `Bytes` for zero).
- `count` is an Integer in the inclusive range **0 through 65,536**. Negative, fractional, nonnumeric and larger requests are semantic invalid arguments: after successful operation dispatch, return a failed Future containing a fresh `InvalidIOArgument`; no backend work and no partial output. Bound selection limits one atomic request and resource abuse; it is **not** a guarantee of 65,536 independent bits of entropy.
- The backend must supply a system-seeded **cryptographically secure** random-byte stream, with OS/provider trust as the external security assumption. `java.util.Random`, time/PID-derived seeds, fixed seeds, sample-stream recycling, silent insecure fallback and Native Image build-time seeded state are forbidden.
- The operation must never return guessed, zero-padded or partially generated bytes after a provider failure. Unavailable/failed secure backends fail closed with the standard general `IOError`. Optional privately enforced host quotas are not a new public quota-policy API; admission failure must not expose partial output or broaden authority.
- `entropy.close()` is the ordinary idempotent, Future-returning `Closable` lifecycle and resolves to its own receiver on success. Close permanently revokes **that grant**, not the host's OS random subsystem or the independent grant held by another Process. Host Process termination also revokes the grant.
- A call after the close cutover fails with a fresh `IOLifecycleError` in its returned Future; `close()` itself commits at invocation, retains existing idempotent-follower semantics and cannot be cancelled back into an open grant.
- A `bytes` result is **committed at atomic publication of the full independently owned Bytes value**. A successful pre-commit cancellation yields no published bytes. An uncommitted accepted request terminated by close fails with `IOLifecycleError`; a committed result remains committed. Host RNG internal state advancement is not an observable reversible effect and need not be rolled back. Runtime/backend work may be cleaned up under host custody without new guest turns.

## 3. Isolation, Actor and P semantics

The live entropy **grant** is **nontransferable** by ordinary `ActorRef.send`, `request`/reply, and `Actor.spawn` initialization: normal graph transfer fails with `NonTransferableValue`. No special `spawn` delegation is introduced. P transfer/capture fails with `NonParallelValue`. A new Actor or imported module does not silently inherit the grant. An Actor cannot manufacture authority from the prototype or `process`.

Completed `Bytes` values are ordinary Protos values. They may be copied/transferred via established Actor/P value semantics, with no sharing of mutable byte-buffer identity across Actors.

**Important HTTP Host detail:** `std:http/Host.owningWithFactory` sends Worker `initialization` through **ordinary Actor value transfer**, not a privileged `Actor.spawn` transfer. Therefore a "spawn-only transferable grant" would not solve that use case and is explicitly **not** part of C. An owner Actor can safely expose `ActorRef` to an **entropy broker** that handles messages, requests `entropy.bytes(count)` and returns completed `Bytes`. The Worker receives only that ActorRef and bytes, not the capability. This costs a message round trip and an actor/service scheduling hop; it may be revisited on measured evidence.

Neither `Closure.parallel` nor the runtime automatically gains entropy authority. There is no new P effect primitive or separate `EntropyReader` delegation type.

## 4. Security, portability and failure boundary

- JVM and installed **Native Image** present one Protos semantic contract; the implementation may use JDK `SecureRandom` or host-native trusted secure providers privately. Runtime initialization must happen securely in the **running target**, never depend on RNG state captured when constructing the native binary image.
- No implicit blocking of an Actor turn, non-Task bootstrap or unavailable suspension environment is allowed. The API returns a Future even when the provider may wait, fail, or be temporarily unavailable; `.value()` uses only previously specified suspension rules.
- Readiness/absence are different from invalid arguments, provider failure and closure. Never turn a missing grant into an insecure fallback or `null` result.
- Runtime/host controls on outstanding work, byte throughput and startup can be private, fail-closed resource protection; they cannot change the semantics of already committed results or grants in unrelated Processes.
- No cryptographic promise about `Bytes` zeroization, secret storage, accidental string conversion, or HMAC/password/JWT security is established. A result can carry secret material and applications must manage it carefully.

## 5. Explicitly rejected or deferred designs

| Alternative | Disposition |
| --- | --- |
| A: ambient global `SecureRandom.bytes` by import | Rejected: violates no-ambient-authority and least privilege |
| B: `process.entropy()` / `process.secureBytes()` | Rejected as default: conflates Process access with a distinct permission |
| **C: separate nontransferable host-provisioned `entropy`** | **APPROVED**: narrow, testable, composable, small present cost |
| D: independently delegable attenuated entropy grants | **Deferred**: potential Worker speed advantage, but requires new transfer/revocation/ownership semantics |
| E: public crypto-provider registry, HSM or policy DSL | Deferred: pays substantial speculative abstraction cost now |
| F: secure generator written purely in Protos | Not an entropy acquisition solution without an externally trusted secure seed |
| G: no change | Rejected: does not unblock the motivating secure-token/salt need |

**Escalation/escape path:** if benchmarked ActorRef broker contention or Worker latency creates an unacceptable cost, investigate the separate **D** style of explicitly delegable/attenuated generation authority. That would require a new owner-approved semantic design; it is not an implementation optimization permitted by D243-C. The existing `bytes(count)` result semantics can remain stable.

## 6. Normative and implementation consequences

The durable decision **does not itself alter product source or `spec/`**. [I157/#1090](https://github.com/guillermomolina/protos/issues/1090) must publish the normative source of truth (with `spec/PROTOS_SPEC_CHANGELOG.md`), CLI/embedding bootstrap wiring, the public capability, JVM/Native backend, cancellation/close, tests, tutorials and developer-facing documentation. Primary new authority owner should be `spec/io/PROCESS_IO.md` for bootstrap plus an appropriate concrete capability specification section; share cross-cutting rules with `IO_CORE.md` rather than duplicating them.

I157 must test 0/maximum/invalid requests, exact independent `Bytes`, import/Tool/Actor/P denial, root-only grant, Native Image RNG safety, no insecure fallback, Future commitment/cancel-close races, per-Process revocation, and the HTTP Worker broker path. A passed build is not cryptographic proof, and a clean static review is not a successful JVM or Native execution.

**Boundary:** D243's decision can be durably ratified and closed independently of its open implementation. D244, D245 and D246 retain independent design approval gates; approving C creates no implicit HMAC, password-hash or JWT policy.
