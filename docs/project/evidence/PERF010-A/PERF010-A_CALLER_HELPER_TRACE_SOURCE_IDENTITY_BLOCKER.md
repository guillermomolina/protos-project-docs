## Why every compilation event reports Src n/a

This is now source-established rather than guessed from the trace.

At the pinned Protos revision, both generated Bytecode DSL root families are created with:

```java
BytecodeConfig.DEFAULT
```

including the semantic wrapper in `ProtosSemanticBytecodeRootNode.wrap(...)`.

In the pinned Truffle Bytecode DSL API, `BytecodeConfig.DEFAULT` explicitly means that no optional source/instrumentation information is materialized during parsing. Source information is lazily reparsed only when requested.

The Truffle `TraceCompilationListener` obtains the printed source through:

```java
target.getRootNode().getSourceSection()
```

and formats a null section as:

```text
n/a
```

Protos already contains a focused test proving the intended materialization mechanism:

```text
src/test/java/com/guillermomolina/protos/execution/
  ProtosPerf006B5BSourceInstrumentationLocationTest.java
```

That test explicitly forces Bytecode DSL source information before asserting locations, using mechanisms including:

```java
root.getRootNodes().ensureComplete();
root.ensureSourceSection();
location.ensureSourceInformation();
```

Thus the zero source-bearing trace events are explained by the existing lazy-source configuration. They are not evidence that the caller semantic root or caller helper was never submitted or compiled.
