## Implementation architecture — owner-requested next work, not yet runtime-validated

**Do not execute withdrawn `@Specialization`-only prompt.** Use existing Bytecode DSL, not a new compiler/IR/optimizer.

**Split into two coherent publication slices within PERF040; neither is independently blocked, scheduled or closed as a new Issue.**

**D1 — canonical numeric admission and non-evicting primitive selector operations (next slice):**

1. At a single *post-freeze* Prelude publication seam, derive an immutable per-Prelude certificate for each canonical primitive arithmetic / ordering selector and receiver family. Certify exact method owner closure, home, prototype chain and frozen state, using existing `canonicalOperationForSelection`/`canonicalRelationForSelection`; no `Assumption` for a frozen canonical graph. Synthetic and alternative Core instances with nonstandard methods must fail closed and retain ordinary dispatch. The code owner must not grant a certificate solely because a field or class says "standard". Keep authority within bootstrap/certifying logic, not guest-writable slots or mutable globals.
2. Lower statically known `+`, `-`, `*`, `/`, `<`, `<=`, `>`, `>=` to distinct built-in Bytecode DSL numeric operation proxies (shared math helpers; no eight parallel math engines). Follow the already-present `@OperationProxy` example `ProtosCanonicalBooleanOneNode`. Keep a `MISS` branch retaining exactly-once operand evaluation and the old ordinary send pipeline.
3. Specialize only authentic primitive `long`/`double` operands initially, including mixed Float rounding and signed-64 exact overflows/division rules. Use disjoint **positive** numeric guard(s) and a **negated domain guard** on `@Specialization ordinaryMiss`; no unconditional catch-all; no `replaces` targeting numeric specializations. Avoid `@Fallback` with the existing multi-instance cached negative-guard issue. Cache immutable certification if needed, but no per-send D013 lookup/assumption in a certified hot branch. Treat genuinely invalid or uncertified sends by returning `MISS`.
4. Prove same-site `generic->numeric` and `numeric->generic->numeric` for add **and** all four ordering relations, while preserving exact canonical overrides/source-vs-dynamic behavior, coercion/rounding, no Complex ordering, normal/DEBUG/reparse, context/Prelude and carrier boundaries. Require structural proof from generated DSL or compiled graph that the primitive lane remains reachable, plus human-executed full/focal tests. Do not claim performance speedup without data.
5. Leave rich numeric operands on their already-correct **ordinary** semantic path in D1. This is a temporary performance boundary with no change to guest behavior; do not add a new rich numeric math engine in D1.

**D2 — rich numeric lanes / complete acceptance (following successful D1 publication):**

1. Extend the selector-specific builtins to genuine `ProtosLargeIntegerValue` (Integer + Integer all shapes) via `ProtosNumericValueSupport`, retaining compact normalization and `@TruffleBoundary` around intrinsically costly BigInteger computation, not the entire dispatch.
2. Add canonical `Fraction` and `Complex` **selection** specializations, keeping execution of the exact trusted source closure where its source semantics are observable; reuse `ProtosNumericValueSupport`, `ProtosComplexArithmetic`, `ProtosStandardFractionProtocol` and `ProtosStandardComplexProtocol`; do not silently bypass source-backed effects. When there is a mechanically provable equivalent direct kernel fast path, it must still satisfy the source/instrumentation/error obligations before adoption.
3. Expand structural/JIT and semantic mixed-family tests across all five number families, stale/wrong-Prelude values, genuine custom receivers/delegates, native transfer/DEBUG/reparse/signed-zero, and small-only pay-as-you-grow; human executes full acceptance, retain separately the PERF040 measured graph/timing admission gate.

**Existing independent ownership remains:** I101 controls independently proved NORMAL constant folding; PERF046 controls numeric-equality and comparison-family performance beyond the shared ordering machinery; PLAT056 / D197 / D198 are not casually reopened. No new Dxxx/PLATxxx or Ixxx identifier asserted. New separate Issue is needed only if the GITHUB006 independent milestone triggers actually arise.
