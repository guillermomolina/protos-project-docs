## Batch contents

TEST009-M accumulated five compilerability repairs before one final expensive
Truffle diagnostic.

### M1 — TextReader StringBuilder cold-path cut

Only the `line.append(unit.text())` inside `ProtosTextReader.scanLine` now
crosses a small `@TruffleBoundary` helper. CR/LF framing, `maxBytes`
accounting, decoder state and the TEST009-K queue repair remain PE-visible and
unchanged.

### M2 — ProtosObjectValue lexical-authority choke points

A new package-private `ProtosLexicalBindingAuthorityCalls` centralizes bounded
generic authority calls for contains/read/snapshot/append/put/remove plus
one-time authority handoff. `ProtosObjectValue` routes generic authority work
through those helpers while retaining the shared empty-authority fast path.

### M3 — ProtosActivation residual authority dispatch

Deferred-authority installation and residual has/read/create/assign operations
reuse the same bounded helpers. Context materialization timing, authority
ownership and frame-native ordinal paths remain unchanged.

### M4 — represented-value generic fallback

Only the generic
`ProtosRepresentedValue.representedDelegationParent(prelude)` projection is
isolated behind a narrow boundary. Existing specific lookup fast paths remain
unchanged; no exhaustive type ladder or semantic cache was introduced.

### M5 — exact native-body identity specialization

`EnterClosureCall` now has a small exact-body `nativeDirect` specialization
with cache limit 3, matching other local PIC limits. The single
ordinary-versus-suspension-capable rule is owned by
`NativeCall.enterNativeBody(body)`; structured-dispatch rejection remains
unchanged and TEST009-J's structured-call family is not reopened.

## Causal reading of M

M's targeted generic expansion seams no longer dominate the retained final
diagnostic. In particular, the old generic lexical-authority,
represented-value and native-body interface-dispatch families targeted by M
were cut substantially enough to expose deeper native-body host/JDK expansion.

The newly visible TooDeepInlining findings group into three observed mechanisms:

1. repeated JDK String-bounds / Preconditions / Formatter / Locale / generic
   reflection expansion reached through specialized native bodies such as
   Encoding;
2. Truffle Bytecode `ConstantsBuffer.mapPut/fillMapFromConsts` expansion when
   C-prime execution plans are constructed from specialized native entry;
3. NIO close / `ConcurrentHashMap.TreeNode.findTreeNode` expansion through
   filesystem resource release.

The second and third mechanisms were not the TEST009-L TextReader
`scanLine` chain.
