# I091-F5 — Adversarial per-occurrence audit of the 73 Java BigInteger references

**Date:** 2026-10-11. **Formal work:** [I091/#869](https://github.com/guillermomolina/protos/issues/869). **Product revision:** [`ced3746f9664ec5ceb562461c077bdf0627e5663`](https://github.com/guillermomolina/protos/commit/ced3746f9664ec5ceb562461c077bdf0627e5663), `0.3.331-SNAPSHOT`.
**Input independently confirmed by owner:** `python3 tools/numeric_dependency_census.py`; 436 Java production files, 20 files matching three numeric symbols, 171 combined tokens, **73 Java BigInteger tokens** in 16 Java production files, current source fingerprint `52cb776b3931489ecd237b172ef958d575f580b606bab8e7c74b7beeeba8e817`.

This report **supersedes the earlier architectural verdict** in [the complete lexical F5 report](I091_F5_COMPLETE_NUMERIC_DEPENDENCY_RECONCILIATION_2026_10_11.md). That report's counts remain valid; the old blanket assertion that every surviving reference is justified is not valid.

## Audit rule: presumption against BigInteger

The maintainer's acceptance criterion is **presumption against** `java.math.BigInteger` everywhere except genuinely exceptional integer arithmetic. For **each** token owner:
1. Is the operand/result mathematically beyond signed-64, or is the method explicitly obliged by an external typed Java/Truffle API to exchange a `java.math.BigInteger`?
2. Could the operation carry a signed-64 `long` or binary64 `double`, or call a numeric capability without allocating/transporting a BigInteger? If so, a mandatory host BigInteger is a **defect**, even if the existing SPI documents it.
3. The **Fraction/Complex test**: if the only reason is “BigInteger is a Number”, would the same consumer accept Fraction/Complex as its universal carrier? If not, the generic boundary is confusing semantic value family with host representation. This test is especially decisive for SPI and transfer records; it is not a claim that Fraction or Complex are mathematically integral.
4. Compare with real implementations: if GraalVM's standard interop or mature Truffle languages offer primitive and large paths, require a reason why Protos should force the expensive path. Conversely, **do not remove a mandatory Java `asBigInteger` export just because it names BigInteger**: the external API's requested return type is an independent proof of a legitimate on-demand conversion.
5. Every counterexample must name its caller, actual creation/cast and minimal repair surface. Do not equate **token counts** with allocations, timings, compilation graphs or number of independent defects.

D188 [ratified source-classified lossless integral admission](../../decisions/language/D188_FOREIGN_VALUES_AND_FOREIGN_MODULE_GUEST_SEMANTICS.md) **does not demand** Java BigInteger universal transport. D197 [ratified semantic types](../../decisions/language/D197_EXACT_NUMERIC_TOWER_AND_NORMALIZATION.md): distinct guest-visible signed-64 `Integer`, `BigInteger`, `Fraction`, `Float`, `Complex`, without equating their semantic representation to any Java class. PLAT056 [Candidate C](../../decisions/platform/PLAT056_PRIMITIVE_FIRST_NUMERIC_GUEST_OBJECT_ARCHITECTURE.md): primitive paths and narrow genuinely large arithmetic, with Java host/interop exceptions only where explicit and necessary. D197's public numeric-tower implementation and `Integer.recognizes` are **not silently authorized** by this audit.

## Two concrete defect chains and exact proposed gates

### A. Public SPI: small Integer crosses host BigInteger unnecessarily

**IN:** `Polyglot Value(42)` → `fitsInBigInteger/asBigInteger` → `ProtosForeignValueClass.integral(BigInteger)` → adapter `(BigInteger)` → internal `normalizedHostInteger` → `Long(42)` → guest Integer.

**OUT:** guest Integer → `ProtosNumericValueSupport.hostInteger` → `Long(42)` → adapter `BigInteger.valueOf(42)` → Polyglot `convert` → `long(42)`.

These are **actual source-level conversion routes**, not a benchmark measurement. The adapter's comment “D188 ... declares every exact Integer as a host BigInteger” misattributes a Java representation choice to D188.

**Implementation acceptance to be separately authorized:** internal provider and public plugin communication must support small-integral `long/Long` without BigInteger allocation, and an exceptional exact large representation when mathematically required. Check both directions, `read/writeElement` indexed domain, source-family admission before `fitsInLong` (do not classify Fraction/Complex/decimal/Float as an Integer solely because bits fit), and faithful failure for huge indices. Do not silently break existing third-party SPI client JARs; adding `integral(long)` *alone* does not fix outbound argument type and may introduce `Long` where older plugins expect `BigInteger`. Either negotiate a provider SPI revision with legacy fallback or prove a compatible opt-in extension, with separate old/new external-JAR conformance.

### B. PLAT051 semantic transfer: generic small Integer leaves need not be BigInteger

`ProtosSemanticTransferPayload.integer(long)` and `integer(Object)` convert **ordinary** signed-64 integers to BigInteger; `RegexSemanticTransferFamily` uses it for ordinary offsets/counts. This is not overflow nor explicitly typed Truffle `asBigInteger`, and **PLAT051 does not select BigInteger** as the mandatory host representation. Distinguish semantic-family leaf tag from physical scalar.

**Acceptance:** `Long` for signed-64 payload leaves and BigInteger only for genuinely large leaves, exact `isInteger`, `nonNegativeInt`, `integerSignum`, `integersDifferBy`, `semanticInteger`, and immutable/portable destination rematerialization. Validate arbitrary precision boundary and `Integer.MIN_VALUE`, `Long.MIN_VALUE`, mixed large/small difference, negative offsets; Actor/P/Process contract, Regex Match and Pattern results, and already published PLAT051 black-box tests. Inspect potential public `get()` compatibility before changing return types.

### C. Explicit typed BigInteger is not universal BigInteger

**Truffle peer evidence directly read in code:**
- [TruffleRuby `RubyBignum.java`](https://github.com/truffleruby/truffleruby/blob/master/src/main/java/org/truffleruby/core/numeric/RubyBignum.java): `RubyBignum` owns large `BigInteger` payload and exposes `fitsInLong/asLong` alongside `asBigInteger`; Java `BigInteger` is not automatically the carrier of ordinary small Ruby integers.
- [GraalPy `PInt.java`](https://github.com/oracle/graalpython/blob/master/graalpython/com.oracle.graal.python/src/com/oracle/graal/python/builtins/objects/ints/PInt.java): rich integer has exact Java BigInteger state, separate `fitsInLong/asLong` and `asBigInteger` exports; this is not evidence every primitive guest integer is a PInt.
- [TruffleSqueak `LargeIntegers.java`](https://github.com/hpi-swa/trufflesqueak/blob/77bbbec529e9869c3b94173235294032576547f8/src/de.hpi.swa.trufflesqueak/src/de/hpi/swa/trufflesqueak/nodes/plugins/LargeIntegers.java): small arithmetic path with overflow fallback, BigInteger used for truly large arithmetic, large→small normalization.
- [TruffleSqueak `JavaObjectWrapper.java`](https://github.com/hpi-swa/trufflesqueak/blob/main/src/de.hpi.swa.trufflesqueak/src/de/hpi/swa/trufflesqueak/interop/JavaObjectWrapper.java): source dispatch prefers `fitsInLong/asLong` when valid; `asBigInteger` exists as a separately requested typed export, and host BigInteger is dealt with specifically, not as a required universal Number scalar.
- [GraalVM `Value` Javadoc](https://www.graalvm.org/truffle/javadoc/org/graalvm/polyglot/Value.html) / [`InteropLibrary` Javadoc](https://www.graalvm.org/truffle/javadoc/com/oracle/truffle/api/interop/InteropLibrary.html): distinct lossless `fitsInLong/asLong` and `fitsInBigInteger/asBigInteger` channels.

**Falsification warning:** no surveyed peer is required to implement PLAT051 or Protos' third-party provider SPI; the comparative conclusion is about **primitive-first numeric transport**, not proof that every other language's entire architecture matches Protos. The peers themselves legitimately use Java BigInteger for large arithmetic and explicitly demanded interoperability. Thus a literal ban “BigInteger anywhere except `long+long` overflow” would break mandatory Java API signatures and mathematically exact rich operations; the sound version is *no unconditional use for ordinary signed-64 values*.
