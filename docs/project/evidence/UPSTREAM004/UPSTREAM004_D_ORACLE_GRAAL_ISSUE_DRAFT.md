### Describe the issue

A minimal generated Bytecode DSL root compiles successfully at Tier 2 on the
JVM, but the same root fails Truffle Tier-2 runtime compilation when executed
inside a Native Image.

The minimum root:

- uses `@GenerateBytecode(enableYield = false)`;
- declares no custom operations;
- has no locals, loops, or yields;
- only returns the constant `1`.

The Native runtime compiler reports:

```text
Object of type Lcom/oracle/truffle/api/impl/FrameWithoutBoxing;
should not be materialized
(must not pass virtual object into an invoke that cannot be inlined)
```

The guest result is still `1` because
`CompilationFailureAction=Print` reports the bailout and execution falls back
to the interpreter. The issue is the failed Tier-2 compilation, not an
incorrect guest result.

On the same `25.5.5-SNAPSHOT` plane, the JVM compiles the same
`MiniPlainRootGen` successfully at Tier 2.

### Code snippet or code repository that reproduces the issue

The root itself is:

```java
@GenerateBytecode(
        languageClass = MiniLanguage.class,
        enableYield = false)
public abstract class MiniPlainRoot extends RootNode implements BytecodeRootNode {
    protected MiniPlainRoot(
            MiniLanguage language,
            FrameDescriptor frameDescriptor) {
        super(language, frameDescriptor);
    }
}
```

The builder only emits:

```java
BytecodeRootNodes<MiniPlainRoot> roots =
        MiniPlainRootGen.create(
                null,
                BytecodeConfig.DEFAULT,
                b -> {
                    b.beginRoot();
                    b.beginReturn();
                    b.emitLoadConstant(1L);
                    b.endReturn();
                    b.endRoot();
                });

MiniPlainRoot root = roots.getNode(0);
root.getBytecodeNode().setUncachedThreshold(0);

RootCallTarget target = root.getCallTarget();
for (int i = 0; i < 64; i++) {
    target.call();
}
```

I can attach the complete standalone Maven reproducer package. It contains no
application code beyond this reproducer.

### Steps to reproduce the issue

The easiest released reproduction uses GraalVM CE 25.3.4.1 and Maven Central:

```bash
JAVA_HOME=/path/to/graalvm-community-25.3.4.1+1.1
PATH="$JAVA_HOME/bin:$PATH"

mvn \
  -Dgraalvm.version=25.3.4.1 \
  -Pnative \
  -DskipTests \
  clean package

./target/native/bug013-min-repro \
  -Dpolyglot.engine.AllowExperimentalOptions=true \
  -Dpolyglot.engine.BackgroundCompilation=false \
  -Dpolyglot.engine.CompileImmediately=true \
  -Dpolyglot.engine.TraceCompilation=true \
  -Dpolyglot.engine.CompilationFailureAction=Print \
  plain
```

Observed:

```text

Object of type Lcom/oracle/truffle/api/impl/FrameWithoutBoxing;
should not be materialized

```

I then repeated the same reproduction using the current developer build
`25.5.5-dev-20260930_0129` and its matching Maven resource bundle /
`25.5.5-SNAPSHOT` dependencies. The same Native bailout occurs.

### Expected behavior

The generated Bytecode DSL root should be able to complete Truffle Tier-2
runtime compilation inside Native Image, as the same root does on the JVM, or
otherwise avoid forcing the virtual `FrameWithoutBoxing` to materialize across
the generated interpreter path.

### Additional context

The generated `MiniPlainRootGen` from the tested snapshot contains:

```java
@Override
public Object execute(VirtualFrame frame) {
    return continueAt(bytecode, 0, stackBase, (FrameWithoutBoxing) frame);
}

private Object continueAt(
        AbstractBytecodeNode bc,
        long bci,
        long sp,
        FrameWithoutBoxing frame) {
    ...
    state = bc.continueAt(this, frame, state);
    ...
}
```

The cached generated interpreter implementation is annotated with
`@BytecodeInterpreterSwitch`, `@ExplodeLoop(MERGE_EXPLODE)`, and
`@EarlyEscapeAnalysis`.

The Native stack trace reaches:

```text
EnsureVirtualizedNode.ensureVirtualFailure
CommitAllocationNode.lower
...
TruffleCompilerImpl.compilePEGraph
TruffleCompilerImpl.compileAST
...
IsolateAwareTruffleCompiler.doCompile0
```

Because the minimum reproducer uses `enableYield=false`, yield/continuation
support is not required for the failure.

I found the older #1463 and #1445 reports with the same general
`FrameWithoutBoxing should not be materialized` diagnostic, but those are
2019 reports in different instrumentation/high-load contexts. This reproducer
is a current Bytecode DSL root, is Native-runtime-compilation-specific, and
still reproduces on the current developer snapshot.
