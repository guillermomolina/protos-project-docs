## Exact question

Determine what Native Image capability contract Protos should expose while
`oracle/graal#14579` prevents generated Truffle Bytecode DSL roots from
reliably completing guest Tier-2 runtime compilation inside Native Image.

The investigation kept distinct:

~~~text
HOST_NATIVE_IMAGE_AOT_COMPILATION
!=
TRUFFLE_GUEST_RUNTIME_COMPILATION
~~~

A Native executable can remain a real AOT-compiled host artifact while Protos
guest execution is interpreter-only.

## Fallback runtime authority

Current GraalVM documentation describes the fallback Truffle runtime as an
interpreter-only runtime and documents:

~~~text
-Dtruffle.UseFallbackRuntime=true
~~~

including Native Image build-time selection.

Relevant public authority used in the investigation:

- https://www.graalvm.org/latest/reference-manual/embed-languages/
- https://www.graalvm.org/latest/reference-manual/native-image/
- https://www.graalvm.org/truffle/javadoc/org/graalvm/polyglot/Engine.html

Current Polyglot API also distinguishes whether a host supports guest compilation
through `Engine.supportsCompilation()`, reinforcing that host AOT and guest
runtime compilation are separate capabilities.

## Relevant Truffle survey

### SimpleLanguage

SimpleLanguage demonstrates a complete Truffle language packaged as Native Image.
The important comparison is that the language implementation can be host-AOT
while guest execution remains governed by the selected Truffle runtime.

Public references:

- https://github.com/oracle/graal/tree/master/truffle/docs
- https://github.com/oracle/graal/tree/master/truffle/src/com.oracle.truffle.sl

### GraalJS

GraalJS has both JVM-hosted and Native Image execution surfaces. Its existence as
a native executable does not imply that "native" and "guest JIT" are synonyms.

Reference:

- https://www.graalvm.org/latest/reference-manual/js/

### TruffleRuby

TruffleRuby Native Standalone retains Truffle guest optimization and documents
different startup/throughput characteristics between hosting modes. It is useful
counter-evidence against treating "Native" as meaning "no guest warm-up/JIT."

Reference:

- https://www.graalvm.org/latest/reference-manual/ruby/

### GraalPy

GraalPy provides the closest capability-matrix precedent: its standalone/native
runtime can operate with runtime JIT disabled, with the consequence represented
as a performance capability difference rather than a Python semantic difference.

References:

- https://www.graalvm.org/python/
- https://www.graalvm.org/latest/reference-manual/python/

### Espresso

Espresso demonstrates a guest VM/language executing inside a host runtime that
may itself be Native Image. Host packaging and guest execution/optimization are
separate layers.

Reference:

- https://www.graalvm.org/latest/reference-manual/espresso/

### Sulong / LLVM

Sulong executes LLVM bitcode through Truffle and dynamically optimizes hot guest
execution under the optimizing runtime. It further demonstrates the distinction
between native host packaging and guest compilation strategy.

Reference:

- https://www.graalvm.org/latest/reference-manual/llvm/

### Apple Pkl

Pkl was considered because it uses GraalVM Native Image, but it is not materially
equivalent to the PLAT045 boundary. Public evidence does not establish the same
"host Native Image containing a Truffle guest runtime whose Tier-2 compiler is
the disputed capability" architecture. It was therefore not used as a primary
precedent.

Reference:

- https://github.com/apple/pkl

## Non-Truffle comparators

### .NET Native AOT

.NET exposes AOT-native deployment while explicitly documenting capabilities
that are unavailable without runtime code generation/JIT. This supports honest
capability matrices around a native executable.

Reference:

- https://learn.microsoft.com/dotnet/core/deploying/native-aot/

### V8 jitless

V8 can preserve JavaScript semantics while running with JIT disabled; the
principal consequence is workload-dependent throughput, not a new JavaScript
language.

Reference:

- https://v8.dev/blog/jitless

### CPython optional JIT

Modern CPython distinguishes whether a build contains/supports JIT capability
and whether it is enabled. This similarly treats runtime optimization as a
separate capability rather than overloading the meaning of the executable format.

Reference:

- https://docs.python.org/3/whatsnew/3.14.html

## Required technical analysis

### Semantic correctness

Candidate B changes no observable Protos semantics. The same guest program remains
executed through the same production Bytecode DSL architecture.

### JVM performance

JVM stays on the optimizing Truffle runtime. JVM Tier-2/JIT remains required and
tested.

### Native startup

The executable remains host-AOT. PLAT045 makes no new quantitative startup claim.

### Native steady-state throughput

Interpreter-only guest execution is expected to be materially slower for hot
long-lived guest workloads. The exact Protos delta is not established in this
decision and must not be invented.

### Memory and executable size

Fallback removes guest runtime compiler activity from the selected Native mode,
but no general memory improvement is claimed. The local candidate executable was
reported at approximately 44.38 MiB; that is evidence, not a contractual size.

### Test Tool and DAP

The local candidate passed maintained Native Test Tool and DAP regression
surfaces. Those checks remain required under the selected capability.

### Other Truffle tooling

Tooling cannot be inferred solely from guest execution success. Every
user-supported Native tooling surface remains subject to maintained admission.
Compilation-specific diagnostics naturally have no successful guest compilation
events in fallback mode.

### Context and multi-Context

No Context semantic or ownership change is selected. Multi-Context performance
under fallback remains a performance/scaling question, not a new semantic model.

### Portability

Candidate B uses an upstream runtime mode and therefore avoids the portability
burden of a private SVM patch. Public OS/architecture/libc promises remain
distribution decisions under PLAT038.

### CI/build cost

The supported Native lane no longer requires positive guest Tier-2 while fallback
is selected, but must prove fallback mode, zero unexpected compilation attempts
or internal compiler failures, and all required conformance/tooling surfaces.
A separate revalidation gate preserves the path back to optimizing Native.

## Pay only for what is needed

The smallest current capability satisfying the demonstrated product requirement
is:

~~~text
JVM=OPTIMIZING
NATIVE=AOT_HOST_PLUS_CORRECT_INTERPRETER_GUEST
~~~

Anything beyond it must justify present cost.

Candidate D would charge current development, CI, security, portability and
release work for private runtime/compiler ownership before Protos has a
demonstrated current Native-only throughput requirement.

## Grow as needed

Candidate B is future-compatible without preimplementing a fork:

~~~text
NOW:
  Native AOT host + interpreter guest

AFTER_UPSTREAM_REPAIR:
  Native AOT host + optimizing guest
~~~

No language semantics, object representation, Context model, stage0/stage1 model,
resource model or distribution model needs to change.

## Concrete restoration cost

Restoring guest JIT requires:

1. stop selecting the fallback runtime for the optimizing Native configuration;
2. restore positive Native guest-compilation admission;
3. pass helper and semantic Bytecode root Tier-2;
4. update capability diagnostics/documentation from unavailable to supported;
5. keep conformance/Test Tool/DAP gates green.

This is bounded runtime/build/test policy work, not a foundational language
migration.

## Failure modes

### User interprets Native as optimized

Mitigation: expose the exact capability matrix. Do not say or imply that guest
JIT is supported.

### Long-running Native workload is too slow

Mitigation: use the still-supported optimizing JVM runtime while the upstream
gate remains closed, or explicitly reopen the platform decision if a Native-only
requirement becomes unavoidable.

### Tool depends on guest compilation

Mitigation: keep supported tooling in Native admission instead of inferring it
from language smoke success.

### Upstream Issue closes without an applicable fix

Mitigation: Issue state alone never re-enables JIT. The objective minimum
reproducer and maintained Protos gates must pass.

### Fallback accidentally leaks into JVM

Mitigation: JVM guest Tier-2 remains independently required.

### Compiler failure is hidden as correct guest fallback

Mitigation: fallback mode deliberately performs no guest JIT; unexpected
compiler/internal failures remain fail-closed and must not be reclassified as
successful guest JIT.

## Future-scenario stress test

### Native-only high-throughput production becomes mandatory

This is the strongest scenario against Candidate B. If it arrives before
upstream repair and JVM deployment is impossible, PLAT045 must be reopened. A
bounded patched-toolchain decision could then be reconsidered with a real present
requirement.

### Many Contexts / high concurrency

The semantic model remains sound. CPU cost may rise because more guest work is
interpreted; measure if this becomes a product requirement.

### Alternative OS/architecture

Upstream fallback mode preserves more implementation freedom than a Protos-owned
SVM patch. Platform support still requires normal distribution validation.

### Bytecode DSL/compiler evolution

Candidate B leaves the production Bytecode DSL intact, so upstream fixes or
evolution can be consumed without undoing an alternate Protos execution
architecture.

### Migration away from Truffle

Candidate B introduces no new lock-in. Candidate D would increase it.

## Mandatory adversarial answers

### 1. Smallest solution satisfying current requirements

Candidate B: preserve optimizing JVM; support Native as real AOT host plus
upstream-supported interpreter-only guest.

### 2. What current requirement justifies capability beyond it?

No demonstrated current requirement justifies private Native guest-JIT repair.
Such a requirement would need a concrete Native-only throughput/latency need
that cannot use the JVM or wait for upstream.

### 3. Can Native guest JIT be restored later without semantic change?

Yes. The evidence locates the limitation in Native runtime compilation rather
than Protos semantics.

### 4. What must be rewritten later?

Fallback selection, Native guest-compilation admission, capability diagnostics
and documentation. No language model rewrite is required.

### 5. What makes a private Graal toolchain regrettable today?

VM-internal patch ownership, recurring rebases, security/version skew,
reproducibility, CI, portability and distribution burden.

### 6. What makes interpreter-only Native regrettable?

A real Native-only sustained-throughput workload whose CPU/latency constraints
make fallback execution insufficient.

### 7. What future requirement makes Candidate B wrong?

Native becomes mandatory for hot long-lived workloads before upstream repair.

### 8. Escape path

Prefer upstream repair and objective revalidation; otherwise retain JVM where
possible; only then reconsider a private bounded toolchain with explicit new
approval.
