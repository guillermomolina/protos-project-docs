## Corrected architectural diagnosis

The required optimization is **not** merely constant-folding the spelling `true.ifTrue() { 1 }`. It must admit any runtime canonical Boolean receiver, including `a.ifTrue() { 1 }` when `a` holds canonical `true` or `false`. In the common case the selector must behave as Boolean control directly, analogously to current primitive numeric `a + a`, **not** as a full ordinary message invocation plus a bolted-on fast branch.

At the pinned I092-native source, `CanonicalToBytecodeLowerer.admitsNativeIfTrue` recognizes selector/arity/frozen root, `emitComposedSend` sets `tryCompactCanonicalIfTrue`, and `emitCanonicalIfTrueLiteralSite` still **emits** native-hit and generic-miss structures together with `PrepareSendOne`, `PrepareStructuredBooleanCall`, a shared B-prime region, and `TryFinally`/`CompleteIfTrueSiteOuter`. The ordinary fallback is semantically necessary for non-Boolean receivers and overridable selectors, but **eagerly emitting all of its lowering at each optimized site is not a required implementation strategy**. IR histograms alone cannot show whether each residual invoke executes on the canonical hit. This record identifies a concrete source-level structural problem and an implementation direction; it does not claim to have proved a specific IR node attribution.

The `CanonicalLiteral.TRUE` lowerer already emits `ProtosBooleanValue.TRUE` as `LoadConstant`. That fact addresses only a trivial spelling. The target requires receiver-polymorphic specialization: for canonical `true`, direct callback activation/execution; for canonical `false`, canonical null, with callback-producing argument still evaluated exactly once; for a non-Boolean/custom receiver, exact ordinary D013 message resolution and invocation. Do not constant-fold or assume that `a` is always Boolean. Do not change the language's observable ordinary-message contract.
