## Exact question and ownership

The child covers PLAT064 matrix facilities **#1 BCI-in-frame, #2 block scoping, #3 materialized locals and #16 cached/uncached transitions**. Decide whether their Protos-specific use is justified or a framework misalignment requiring action. Unlike a performance optimization or a Native Image workaround search, a demonstrated framework correction would not need a speedup proof; nevertheless, an unproven defect does not warrant automatic implementation.

Existing decisions remain binding:
- [PLAT036/#702](https://github.com/guillermomolina/protos/issues/702) selects the frame-backed **single binding-value authority** and stable, ordinary first-class execution contexts with dynamic overflow, retaining captures by reference.
- [D179/#703](https://github.com/guillermomolina/protos/issues/703) selected **C0** after reconsideration; `PRESENT -> ABSENT` removal and subsequent creation on an open execution context are legal. The historical C3 choice was superseded; [I071/#717](https://github.com/guillermomolina/protos/issues/717) implemented the presence-aware model.
- PLAT041–043, PLAT045 and PLAT062 own root roles, execution/continuation and Closure lowering. The materialized-local audit does **not** authorize root merging, a second lexical store or a new closure representation.
- [I110/#912](https://github.com/guillermomolina/protos/issues/912) independently owns approved Boolean primitive-carrier work; as of inspection the Issue is open/ready. PLAT064-A neither reopens nor blocks it.
- [PLAT064-B/C/D/E](https://github.com/guillermomolina/protos/issues/911) remain separate research owners. PLAT064-A completion does not settle their questions.

## Truffle API truth — separate three concerns

Primary upstream source: [GenerateBytecode.java](https://github.com/oracle/graal/blob/95ce1499c8c96ab7d5a6697c5b4bf42160f3b68b/truffle/src/com.oracle.truffle.api.bytecode/src/com/oracle/truffle/api/bytecode/GenerateBytecode.java), [MaterializedLocalAccessor.java](https://github.com/oracle/graal/blob/95ce1499c8c96ab7d5a6697c5b4bf42160f3b68b/truffle/src/com.oracle.truffle.api.bytecode/src/com/oracle/truffle/api/bytecode/MaterializedLocalAccessor.java), [IllegalLocalExceptionTest.java](https://github.com/oracle/graal/blob/95ce1499c8c96ab7d5a6697c5b4bf42160f3b68b/truffle/src/com.oracle.truffle.api.bytecode.test/src/com/oracle/truffle/api/bytecode/test/IllegalLocalExceptionTest.java).

1. **Physical lifetime:** `enableBlockScoping=true` by default. A local created directly beneath `beginRoot()` remains root-scoped; one created under an inner `beginBlock()` can be cleared/reused at Block exit. Setting block scoping false keeps all locals root-scoped and removes lifetime metadata. Root-scoped bindings and Block-scoped compiler temporaries must not be confused.
2. **Materialized access:** `enableMaterializedLocalAccesses=false` by default. When enabled, generated `LoadLocalMaterialized` and `StoreLocalMaterialized` and custom `MaterializedLocalAccessor` may address a lexically enclosing root's local via a supplied materialized frame. Static lexical scope validation does **not** prove that a root later invoked dynamically accesses a still-valid Block-scoped local.
3. **BCI storage:** `storeBytecodeIndexInFrame=false` by default. When true, Truffle can dynamically check materialized-local scope and provide fast BCI access outside the current operation, at the price of additional frame storage/writes. `@Bind("$bytecodeIndex")` already provides BCI inside an operation. This flag is a guard/diagnostic option, not a proof of lexical owner identity.
4. **Accessor identity:** `MaterializedLocalAccessor` retains `rootIndex`, `localOffset`, `localIndex` and resolves the declaring root via the current `BytecodeRootNodes` group before accessing the supplied frame. Thus the physical correspondence of **group/root index/layout** and the materialized frame's owner is independently relevant; an equal lexical name is not a substitute for it.
5. **Tier/reparse lifetime:** `BytecodeLocation.update()` and the current `BytecodeNode` are the suitable APIs for metadata that may change after instrumenting or cached/uncached transitions. A permanently retained old `BytecodeNode` is not a universal safe representation.

**Attempted falsification:** imagine an accessor generated for group G1/root index R that receives a retained frame from an unrelated group G2 with a semantically equal local name and offset. Its `rootIndex` is relative to the generated group; an arbitrary frame must not be assumed physically interchangeable. Protos contains static owner-group admission restrictions and fallback that aim to exclude this condition. **No reachable concrete failure path or failing test was established.** A comprehensive proof for every combination of independent rebuild, Yield, cleanup and reparse is also not established. These limitations remain acknowledged, **not** manufactured blockers requiring new work.

Independent negative evidence:
- No demonstrated need for fast BCI outside operations that requires globally storing BCI in every frame.
- No demonstrated out-of-scope materialized binding with a Block-local implementation temporary as captured owner.
- No demonstrated wrong captured owner after cached/uncached transition that survives existing current-node and tests.
- No demonstrated correctness or footprint reason to disable `enableBlockScoping`.
- No demonstrated safe win from removing materialized-access capability on the auxiliary root without the separate PLAT064-C reachability audit.
- No benchmark or fresh test result; no performance claim.

## Proportionality, deferral and closure

- Smallest sufficient choice: retain existing three generator options and the existing tier metadata handling.
- Cost of premature change: global BCI frame writes/footprint; potential new identity guard on hot paths; or a PLAT036/D179 architectural migration for a failure not observed.
- Cost of deferral: if a real failing out-of-scope materialized access appears, enable supported diagnostic BCI or add a strictly proven guard on the failing consumer; either is an internal host-level correction that need not change Protos semantics. If exact 25.4.4.1.1 processor internals matter to such a fix, verify the published artifact then.
- Future stressors (more Contexts/Actors, scheduler changes, native/AOT, Bytecode DSL updates, increased reparse/continuation frequency) remain governed by already-ratified isolation, context and suspension contracts. No evidence from this child demands preimplementation of future machinery.
- Strongest argument against KEEP: a mixed physical root-group/frame mismatch might remain undetected without a dynamic identity check. Counterweight: current admission/fallback architecture and regressions already address observed risks, and no reachable failure was established; a broad new proof or runtime guard is not proportional.
