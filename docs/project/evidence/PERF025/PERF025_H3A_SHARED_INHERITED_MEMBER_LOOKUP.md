## Investigation result consumed by H3A

The preceding shared-shape/member-lookup investigation established that the
first useful bounded slice does **not** require a general object Shape,
`DynamicObject` migration, ordinal own-slot storage, or a new platform
decision.

The admitted case is narrower:

```text
distinct exact ordinary receiver objects
+
same exact direct parent
+
selector absent locally on the actual receiver
+
D013-guardable lookup beginning at that parent
```

For this case, the inherited selection can be shared while receiver-local
shadowing remains a dynamic guard.

The existing exact-receiver PIC remains authoritative for own-local repeated
reads and all cases not admitted by the shared inherited path.

## Published runtime shape

The product revision adds a backend-private direct-parent projection on
`ProtosObjectValue` and a `ProtosValueLookup.SharedInheritedLookup` carrier
containing:

```text
exactParent
parentLookup
    selected value
    selected home
    D013 selector-specific Assumption
```

Shared lookup establishment is:

```text
exact ordinary receiver only
receiver does not own selector locally
direct parent exists
lookupGuarded(parent, selector, prelude)
```

The lookup therefore begins at the parent rather than at the sibling receiver.
Sibling receivers are not individually registered as D013 dependencies for the
shared inherited selection.

The valid-hit guard checks:

```text
exact ordinary receiver class
same exact direct parent identity
selector still absent locally on actual receiver
cached parent-chain Assumption still valid
```

## Bytecode specialization order

Both generated Bytecode root families now expose two bounded ordinary
`ReadMember` specializations in this order:

```text
1. guardedSharedInherited
2. guardedExactReceiver
3. generic perform fallback
```

The shared inherited specialization is intentionally declared first so several
sibling receiver identities do not consume the exact-receiver PIC entries
before the parent-shared path can apply.

Both specialization levels retain limit `3`.

The generic fallback remains unchanged and authoritative after specialization
replacement or for unsupported runtime representations.

## Mutation and invalidation behavior

H3A preserves selector-specific D013 invalidation.

### Receiver-local shadow creation

If one sibling creates the selected selector locally:

```text
shared parent-chain Assumption remains valid
that sibling fails the local-absence guard
other siblings remain eligible for the same shared selection
```

This avoids invalidating unrelated siblings merely because one receiver gains a
local shadow.

### Receiver-local shadow removal

After that sibling removes the local shadow, the same shared parent descriptor
may match it again if the parent-chain Assumption remains valid.

### Parent or ancestor mutation

Assignment, removal, or nearer establishment of the selected selector on the
parent/ancestor chain invalidates the cached parent lookup through the existing
D013 dependency machinery.

A later lookup establishes a fresh selection and home.

### Unrelated selectors

Mutations of unrelated selector names do not invalidate the selected lookup.

## Closure extraction semantics

The shared path caches selection, not the semantically observable extracted
Closure.

Every hit still executes:

```text
materializeMemberRead(actualReceiver, cachedSelection)
```

Therefore a selected `ProtosClosureValue` is rebound on each extraction with:

```text
capturedReceiver = actual sibling receiver
methodHome = cached selected owner
fresh Closure identity = YES
```

This preserves the existing CALLABLES contract for repeated extraction and for
different sibling receivers inheriting the same method.

## Scope deliberately not implemented

H3A does **not** introduce:

- a general Protos Shape or layout registry;
- Graal `DynamicObject` / `Shape`;
- shared own-local location lookup;
- ordinal `Object[]` local storage;
- selector interning as a new object-model requirement;
- global/static guest state;
- a new semantic or platform decision.

Current `LinkedHashMap<String,Object>` ordinary slot storage is sufficient for
this inherited-selection slice.

A future optimization for distinct objects with the same own-local layout would
need a real location-bearing representation rather than merely reusing this
parent-sharing descriptor. That broader architecture is not silently embedded
in PERF025-H3A.
