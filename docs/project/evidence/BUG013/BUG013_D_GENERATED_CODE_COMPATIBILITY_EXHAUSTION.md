## IGV localization

`CompilationFailureAction=Diagnose` produced runtime-compilation IGV graphs for
both generated root families.

The helper graph retained an `InvokeWithExceptionNode` targeting:

```text
ProtosBytecodeRootNodeGen$CachedBytecodeNodeTailCall.continueAt(
    ProtosBytecodeRootNodeGen,
    FrameWithoutBoxing,
    ...)
```

The same graph then contained a `CommitAllocationNode` attempting to materialize
the `FrameWithoutBoxing` while the virtual-object state retained
`ensureVirtual=true`.

The semantic graph independently retained an `InvokeWithExceptionNode`
targeting:

```text
ProtosSemanticBytecodeRootNodeGen$ContinuationRootNodeImpl.execute(VirtualFrame)
```

and reached the same `CommitAllocationNode` / `ensureVirtual=true` conflict.

This evidence narrowed the failure from a generic frame-virtualization symptom
to surviving Java call boundaries in the Native runtime compiler.

## Source-level interpretation

The Graal 25.4.4.1.1 source confirms that the frame materialization is not a
permitted ordinary fallback:

- `NewFrameNode` creates the `FrameWithoutBoxing` virtual object with
  `ensureVirtualized=true`;
- its source comment states that this condition may only be lifted by an
  `AllowMaterializeNode`, corresponding to an explicit `frame.materialize()`;
- `EnsureVirtualizedNode.ensureVirtualFailure(...)` emits the exact
  `must not pass virtual object into an invoke that cannot be inlined` reason
  when the next fixed node is an `Invoke`.

Therefore changing the virtual-object contract to allow arbitrary frame
materialization would hide the defect by weakening a Truffle compiler invariant.
It is not an acceptable Protos repair.
