## Hosted runtime-compilation preparation

`TruffleFeature.TruffleAllowInliningPredicate` deliberately refuses hosted
runtime-compilation-preparation inlining for methods annotated `@ExplodeLoop`:
its source states that such a method cannot be inlined at that stage because its
loops would no longer be exploded.

The cached generated Bytecode DSL `continueAt` is annotated:

```text
@ExplodeLoop(kind = MERGE_EXPLODE)
```

`HostInliningPhase` also denies trivial host inlining for
`BytecodeInterpreterSwitch` methods.

These policies intentionally preserve a method boundary during Native image
construction; preserving that boundary is not itself the defect, because the
method may still be represented by a runtime graph and consumed later by
Truffle partial evaluation.

## Runtime partial evaluation expects to inline

The Truffle partial evaluator treats an ordinary `@ExplodeLoop` method as an
inlineable PE method unless another directive says otherwise:

- `PartialEvaluator.computePartialEvaluationMethodInfo(...)` assigns the loop
  explosion kind separately from its normal `InlineKind.INLINE` decision;
- `PEAgnosticInlineInvokePlugin.shouldInlineInvoke(...)` delegates to
  `partialEvaluator.asInlineInfo(method)` for ordinary direct calls;
- `PEGraphDecoder.tryInline(...)` attempts to consume an encoded callee graph
  when the call is direct, the method is not `hasNeverInlineDirective()`, the
  inline plugin allows inlining, and the invoke's `InlineControl` is normal.

Therefore there is an intentional two-stage model:

```text
HOSTED_IMAGE_PREPARATION:
  preserve selected PE boundaries

RUNTIME_TRUFFLE_PE:
  reopen/inline those boundaries from encoded runtime graphs
```

BUG013 occurs when a boundary survives into the point where the protected frame
would need to escape.

## Important SVM gate: encoded graph availability

`SubstrateMethod.hasNeverInlineDirective()` contains a Native-specific rule:

```text
real NEVER_INLINE flag
OR
encodedGraphStartOffset < 0
```

Its source comment explicitly says a method with no graph in the image must
never be considered for inlining.

This check occurs in `PEGraphDecoder.tryInline()` before encoded-graph lookup.
Consequently, a missing runtime graph does **not** need to produce a separate
`Graph not available` failure. PE may simply retain the invoke, after which
escape analysis reaches the protected `FrameWithoutBoxing` and emits the
observed materialization bailout.

This corrects an earlier working hypothesis that absence of a graph would
necessarily have generated a separate decoder error.

## Persistent NEVER_INLINE flag is not explained by Truffle trivial-inlining policy

`AnalysisMethod` snapshots its never-inline state from
`SVMHost.hasNeverInlineDirective(wrapped)`.

At this Graal revision that method returns true only for:

- `@NeverInline`;
- `@DontInline`; or
- an explicit `-H:NeverInline=...` method filter.

The separate `registerNeverInlineTrivialHandler(...)` mechanism used by Truffle
does not set this persistent directive.

No current evidence shows that generated `continueAt` or
`ContinuationRootNodeImpl.execute` carries `@NeverInline` / `@DontInline` or an
explicit Native Image method filter.

Thus, for these generated methods, the important remaining branch of
`SubstrateMethod.hasNeverInlineDirective()` is runtime graph availability.

## How runtime graphs receive an encoded offset

`RuntimeCompiledMethodSupport` encodes runtime graphs and assigns an
`encodedGraphStartOffset` only for entries in its `runtimeGraphs` map.

A `RuntimeCompileTask` creates such an entry after decoding and optimizing the
runtime variant. `RuntimeCompilationFeature.onCompileQueueCreation(...)`
constructs the input stream as runtime method variants satisfying:

```text
method != null
AND method.getWrapped().isImplementationInvoked()
AND method not invalidForRuntimeCompilation
```

Only those methods flow through graph encoding and receive a runtime graph
offset.

The runtime-analysis policy can create/link a full runtime variant for a
non-inlined callee when the callee is an allowed runtime-compilation candidate,
so the hosted `@ExplodeLoop` no-inline decision alone does **not** prove graph
absence.

## Rejected / unproven explanations

The following must not be stated as established causes:

### `InlineControl=BytecodesOnly`

The IGV string dump lists enum symbols around the invoke, but that textual dump
does not establish the selected enum value. Source inspection shows
`BytecodesOnly` is explicitly assigned for partial-intrinsic exits and
invocation-plugin fallbacks; there is no evidence yet that the generated
`continueAt` call follows either path.

```text
BYTECODES_ONLY_CAUSE=UNPROVEN
```

### `@ExplodeLoop` directly removes the runtime graph

`@ExplodeLoop` does prevent one hosted inlining step, but the runtime-analysis
policy can still link a full runtime variant for a non-inlined candidate.

```text
EXPLODE_LOOP_DIRECT_GRAPH_REMOVAL=UNPROVEN
```
