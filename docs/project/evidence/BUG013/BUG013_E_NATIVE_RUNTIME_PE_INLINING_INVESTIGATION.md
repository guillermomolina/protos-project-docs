## Hosted runtime-compilation preparation

`TruffleFeature.TruffleAllowInliningPredicate` deliberately refuses hosted
runtime-compilation-preparation inlining for methods annotated `@ExplodeLoop`:
its source states that such a method cannot be inlined at that stage because its
loops would no longer be exploded.

The cached generated Bytecode DSL `continueAt` is annotated:

```text
@ExplodeLoop(kind = MERGE_EXPLODE)
```

`HostInliningPhase` also denies trivial host inlining for
`BytecodeInterpreterSwitch` methods.

These policies intentionally preserve a method boundary during Native image
construction; preserving that boundary is not itself the defect, because the
method may still be represented by a runtime graph and consumed later by
Truffle partial evaluation.

## Runtime partial evaluation expects to inline

The Truffle partial evaluator treats an ordinary `@ExplodeLoop` method as an
inlineable PE method unless another directive says otherwise:

- `PartialEvaluator.computePartialEvaluationMethodInfo(...)` assigns the loop
  explosion kind separately from its normal `InlineKind.INLINE` decision;
- `PEAgnosticInlineInvokePlugin.shouldInlineInvoke(...)` delegates to
  `partialEvaluator.asInlineInfo(method)` for ordinary direct calls;
- `PEGraphDecoder.tryInline(...)` attempts to consume an encoded callee graph
  when the call is direct, the method is not `hasNeverInlineDirective()`, the
  inline plugin allows inlining, and the invoke's `InlineControl` is normal.

Therefore there is an intentional two-stage model:

```text
HOSTED_IMAGE_PREPARATION:
  preserve selected PE boundaries

RUNTIME_TRUFFLE_PE:
  reopen/inline those boundaries from encoded runtime graphs
```

BUG013 occurs when a boundary survives into the point where the protected frame
would need to escape.

## Important SVM gate: encoded graph availability

`SubstrateMethod.hasNeverInlineDirective()` contains a Native-specific rule:

```text
real NEVER_INLINE flag
OR
encodedGraphStartOffset < 0
```

Its source comment explicitly says a method with no graph in the image must
never be considered for inlining.

This check occurs in `PEGraphDecoder.tryInline()` before encoded-graph lookup.
Consequently, a missing runtime graph does **not** need to produce a separate
`Graph not available` failure. PE may simply retain the invoke, after which
escape analysis reaches the protected `FrameWithoutBoxing` and emits the
observed materialization bailout.

This corrects an earlier working hypothesis that absence of a graph would
necessarily have generated a separate decoder error.

## Persistent NEVER_INLINE flag is not explained by Truffle trivial-inlining policy

`AnalysisMethod` snapshots its never-inline state from
`SVMHost.hasNeverInlineDirective(wrapped)`.

At this Graal revision that method returns true only for:

- `@NeverInline`;
- `@DontInline`; or
- an explicit `-H:NeverInline=...` method filter.

The separate `registerNeverInlineTrivialHandler(...)` mechanism used by Truffle
does not set this persistent directive.

No current evidence shows that generated `continueAt` or
`ContinuationRootNodeImpl.execute` carries `@NeverInline` / `@DontInline` or an
explicit Native Image method filter.

Thus, for these generated methods, the important remaining branch of
`SubstrateMethod.hasNeverInlineDirective()` is runtime graph availability.

## How runtime graphs receive an encoded offset

`RuntimeCompiledMethodSupport` encodes runtime graphs and assigns an
`encodedGraphStartOffset` only for entries in its `runtimeGraphs` map.

A `RuntimeCompileTask` creates such an entry after decoding and optimizing the
runtime variant. `RuntimeCompilationFeature.onCompileQueueCreation(...)`
constructs the input stream as runtime method variants satisfying:

```text
method != null
AND method.getWrapped().isImplementationInvoked()
AND method not invalidForRuntimeCompilation
```

Only those methods flow through graph encoding and receive a runtime graph
offset.

The runtime-analysis policy can create/link a full runtime variant for a
non-inlined callee when the callee is an allowed runtime-compilation candidate,
so the hosted `@ExplodeLoop` no-inline decision alone does **not** prove graph
absence.

## Rejected / unproven explanations

The following must not be stated as established causes:

### `InlineControl=BytecodesOnly`

The IGV string dump lists enum symbols around the invoke, but that textual dump
does not establish the selected enum value. Source inspection shows
`BytecodesOnly` is explicitly assigned for partial-intrinsic exits and
invocation-plugin fallbacks; there is no evidence yet that the generated
`continueAt` call follows either path.

```text
BYTECODES_ONLY_CAUSE=UNPROVEN
```

### `@ExplodeLoop` directly removes the runtime graph

`@ExplodeLoop` does prevent one hosted inlining step, but the runtime-analysis
policy can still link a full runtime variant for a non-inlined candidate.

```text
EXPLODE_LOOP_DIRECT_GRAPH_REMOVAL=UNPROVEN
```

## Narrowed next proof obligation

The source investigation has reduced the next diagnostic to the image-build
runtime-compilation inventory for the two concrete surviving callees:

```text
ProtosBytecodeRootNodeGen$CachedBytecodeNodeTailCall.continueAt
ProtosSemanticBytecodeRootNodeGen$ContinuationRootNodeImpl.execute
```

For each method, determine whether the failing Native candidate includes a
runtime-compilation graph / encoded graph offset.

The existing Native Image hosted option:

```text
-H:+PrintRuntimeCompileMethods
```

is the first bounded runtime-image discriminator, but its result is
**asymmetric**.

`PrintRuntimeCompileMethods` is built from `CallTreeInfo`, whose inclusion
criteria are a reachable runtime variant, no runtime-compilation invalidation,
and a non-null analyzed graph. The later encoder input is narrower:
`onCompileQueueCreation(...)` additionally requires
`method.getWrapped().isImplementationInvoked()`.

Therefore presence in the printed inventory does not by itself prove that the
method enters `methodsToCompile` or receives an `encodedGraphStartOffset`.

Decision table:

```text
CALLEE_ABSENT_FROM_RUNTIME_COMPILE_METHODS:
  no eligible analyzed runtime variant is present
  -> encoded runtime graph absence is established for this path
  -> PE cannot reopen the boundary from an encoded graph

CALLEE_PRESENT_IN_RUNTIME_COMPILE_METHODS:
  reachable analyzed runtime variant is established
  -> encodedGraphStartOffset is still NOT proven
  -> next discriminate is isImplementationInvoked / actual methodsToCompile
  -> only after encoded-graph presence is proven inspect directness / InlineControl
```

`PEGraphDecoder.tryInline()` does not emit a TraceInliningDetails message for
its early returns on non-direct invokes, `hasNeverInlineDirective()`, or
non-normal `InlineControl`. The already-collected runtime trace therefore
cannot distinguish those gates without an additional image-build discriminator.

## Helper-side source-level causal chain

Source review at `oracle/graal vm-25.4.4.1.1` closes the helper-side
reachability mechanism.

Generated Bytecode DSL code performs the cached-tier transition as:

```text
transitionToCached()
  -> CompilerDirectives.transferToInterpreterAndInvalidate()
  -> oldBytecode.toCached(...)
```

With `enableTailCallHandlers=true`, generated `toCached(...)` selects
`CachedBytecodeNodeTailCall.create(...)` when `TruffleOptions.AOT` is true.

`TruffleOptions.AOT` is initialized from `ImageInfo.inImageCode()`, so the
AOT branch is true in Native Image execution.

The Truffle graph-builder plugin intrinsifies
`transferToInterpreterAndInvalidate()` as a
`DeoptimizeNode(InvalidateReprofile, TransferToInterpreter)`.
`AbstractDeoptimizeNode` extends `ControlSinkNode`.

Therefore the runtime-compilation graph cannot continue past the deopt point
into `toCached(...)`; the cached allocation is invisible to the compiled
runtime points-to/callee graph. The interpreter nevertheless executes that code
after deoptimization and can create `CachedBytecodeNodeTailCall` at Native
runtime.

This explains the measured asymmetry:

```text
UncachedBytecodeNodeTailCall.continueAt%%R(...) = PRESENT
CachedBytecodeNodeTailCall.continueAt%%R(...)   = ABSENT
```

The resulting helper-side causal chain is:

```text
runtime graph
  -> deopt control sink
  X  cached allocation not discovered

interpreter after deopt
  -> CachedBytecodeNodeTailCall exists

later runtime PE
  -> cached continueAt survives as an invoke
  -> no encoded runtime graph
  -> hasNeverInlineDirective()
  -> FrameWithoutBoxing materialization bailout
```

The semantic `ContinuationRootNodeImpl.execute` omission remains a separate
reachability question and must not be attributed to this deopt edge without
direct evidence.

## New narrowed causal question

Graal Bytecode DSL generation shows that the root transition to cached bytecode
is explicitly interpreter-only:

```text
transitionToCached()
  -> transferToInterpreterAndInvalidate()
  -> oldBytecode.toCached(...)
```

When tail-call handlers are enabled under `TruffleOptions.AOT`,
`toCached(...)` constructs `CachedBytecodeNodeTailCall`.

The next causal question is therefore no longer whether runtime graphs are
missing; that is established. It is why SVM runtime-variant reachability fails
to connect the cached implementation and generated continuation root even
though those objects/methods can participate in Native execution.

The next discriminator should inspect the runtime-compilation call tree /
receiver implementation set around the generated root `continueAt` dispatch.
A useful result would distinguish:

```text
RUNTIME_DISPATCH_SET_CONTAINS_ONLY_UNCACHED:
  points-to/runtime-variant reachability mismatch is localized

RUNTIME_DISPATCH_SET_CONTAINS_CACHED_BUT_NO_RUNTIME_VARIANT:
  candidate registration/variant creation is the next defect boundary
```

No frame-materialization relaxation is justified by this result.

## Cached-transition reachability mechanism

Source inspection of `oracle/graal@vm-25.4.4.1.1` explains how the measured
helper-method omission can arise without the cached implementation being dead at
Native runtime.

The generated Bytecode DSL root emits `transitionToCached()` as:

```text
transferToInterpreterAndInvalidate()
oldBytecode = this.bytecode
newBytecode = insert(oldBytecode.toCached(...))
...
BYTECODE_UPDATER.compareAndSet(..., newBytecode)
```

For a tail-call-handler model under AOT, `toCached(...)` selects
`CachedBytecodeNodeTailCall`. `TruffleOptions.AOT` is backed by
`ImageInfo.inImageCode()`, so the Native executable takes that AOT branch.

The Graal Truffle graph-builder plugin intrinsifies
`CompilerDirectives.transferToInterpreterAndInvalidate()` to:

```text
DeoptimizeNode(
    InvalidateReprofile,
    TransferToInterpreter)
```

and `DeoptimizeNode` inherits from `AbstractDeoptimizeNode`, which inherits
from `ControlSinkNode`.

Therefore the runtime-compilation graph terminates at the transfer boundary
before the generated `toCached(...)` allocation. Interpreter execution after
the deoptimization can still run the remaining Java bytecodes and install the
cached node, while the runtime-compilation analysis graph need not discover the
cached implementation through that path.

Combined with the clean image inventory, the current helper-root causal model is:

```text
runtime analysis sees uncached continueAt
  -> transitionToCached reaches transferToInterpreterAndInvalidate
  -> compiled graph terminates at DeoptimizeNode / ControlSinkNode
  -> post-deopt CachedBytecodeNodeTailCall allocation is not represented there
  -> cached continueAt has no analyzed runtime variant / encoded graph
  -> Native runtime PE sees an actual cached receiver later
  -> SubstrateMethod has no encoded graph and is non-inlineable
  -> FrameWithoutBoxing reaches surviving invoke
  -> ensureVirtualized bailout
```

The first half (missing exact runtime variants) is measured. The attribution of
the missing cached variant specifically to the post-deopt allocation path is a
source-backed causal hypothesis until an explicit reachability-forcing control
is run.

### Planned causal control

Native Image's public `BeforeAnalysisAccess.registerAsInHeap(Class<?>)` API can
force static analysis to assume that instances of a selected class exist at
runtime without changing Protos source semantics.

A temporary image-build Feature can therefore mark only:

```text
ProtosBytecodeRootNodeGen$CachedBytecodeNodeTailCall
ProtosSemanticBytecodeRootNodeGen$ContinuationRootNodeImpl
```

as in-heap.

The control is decisive:

```text
FORCED_TYPES_GAIN_RUNTIME_VARIANTS
AND FRAMEWITHOUTBOXING_DISAPPEARS:
  missing runtime reachability/graph preparation is causally confirmed

FORCED_TYPES_GAIN_RUNTIME_VARIANTS
BUT FRAMEWITHOUTBOXING_REMAINS:
  graph absence was real but not sufficient; inspect next PE gate

FORCED_TYPES_DO_NOT_GAIN_RUNTIME_VARIANTS:
  type-instantiation reachability is insufficient; explicit runtime-method
  registration/variant creation becomes the next discriminator
```

This control changes only image-build reachability assumptions and does not
relax frame virtualization or Native admission.

## Semantic continuation-root refinement

Current generated-source evidence shows that
`ProtosSemanticBytecodeRootNodeGen$ContinuationRootNodeImpl` is constructed
while the bytecode builder finishes a newly created root and is written into
the generated constant pool.

This differs from the helper cached interpreter tier: the continuation root
object itself is **not** first created behind `transitionToCached()` or its
deoptimization control sink.

Its generated `execute(VirtualFrame)` is an ordinary `RootNode.execute`
override and no `TruffleBoundary`, `TruffleCallBoundary`, or other explicit
runtime-compilation exclusion has been identified.

The failing runtime IGV resolves the surviving call to the exact method:

```text
ProtosSemanticBytecodeRootNodeGen$ContinuationRootNodeImpl.execute(VirtualFrame)
```

while the clean runtime-compilation inventory contains no corresponding
`execute%%R`.

SVM source narrows the omission further. From a `RUNTIME_COMPILED_METHOD`
caller, `RuntimeCompilationAnalysisPolicy.determineCallees(...)` creates a
full runtime variant only when the concrete implementation appears in that
runtime caller's `InvokeTypeFlow` and passes the runtime-compilation
predicate. No continuation-specific rejection was found in
`TruffleFeature.allowRuntimeCompilation()`.

A previous working hypothesis that lazy `RootNode.getCallTarget()` alone hides
the continuation type is not established. Truffle explicitly registers the
concrete `createOptimizedCallTarget(..., RootNode)` path as an analysis root,
and PointsToAnalysis initializes object parameter flows from their declared
types. The precise semantic-side loss point is therefore the runtime-variant
receiver/callee flow or registration, not proven object reachability failure.

```text
CONTINUATION_OBJECT_CREATED_DURING_BYTECODE_BUILD=YES
CONTINUATION_EXECUTE_EXPLICITLY_BLOCKLISTED=NO_EVIDENCE
CONTINUATION_EXECUTE_RUNTIME_VARIANT=ABSENT
SEMANTIC_LOSS_POINT=RUNTIME_VARIANT_INVOKE_TYPEFLOW_OR_REGISTRATION
LAZY_CALL_TARGET_AS_SOLE_CAUSE=NOT_PROVEN
```

The SVM API
`RuntimeCompilationFeature.prepareMethodForRuntimeCompilation(...)` provides a
direct causal discriminator: force-register one missing callee at a time and
observe whether its runtime graph appears and the Native Tier-2 bailout changes.

## Instance-method runtime registration correction

A direct call to
`RuntimeCompilationFeature.prepareMethodForRuntimeCompilation(...)` was tested
for the helper-side cached `continueAt`. The Feature executed successfully,
but the clean runtime-compilation inventory still contained zero methods from
`CachedBytecodeNodeTailCall`.

This does **not** show that explicit runtime registration is ineffective.
`PointsToAnalysis.addRootMethod(...)` treats instance methods specially:
`otherRoots` such as `RUNTIME_COMPILED_METHOD` are not directly rooted.
Instead, their linking is deferred to callee resolution of the context-
insensitive invoke flow.

For `invokeSpecial=true`, resolution requires the declaring class to be
instantiated in points-to analysis. Thus:

```text
prepareMethodForRuntimeCompilation(instance method)
  -> nominal runtime variant exists
  -> original special invoke is rooted
  -> runtime variant waits for declaring-class instantiation
  -> no instantiation => no linked/reachable %%R
```

This matches the cached Bytecode DSL case: the actual
`CachedBytecodeNodeTailCall` allocation occurs only after
`transferToInterpreterAndInvalidate()`, behind a deoptimization control sink,
so hosted analysis does not observe the class instantiation.

The corrected next discriminator is to mark
`CachedBytecodeNodeTailCall` as instantiated with
`BeforeAnalysisAccess.registerAsInHeap(...)` and then call
`prepareMethodForRuntimeCompilation(...)` for its `continueAt`.

A transition from absent to present `continueAt%%R` would directly establish
missing hosted type instantiation / callee resolution as the helper-side root
cause.
